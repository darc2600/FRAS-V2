# Appendix C: Database Schema Documentation

## C.1 Overview

This appendix documents the PostgreSQL database schema of the Facial Recognition Attendance System (FRAS). The schema was analyzed from the repository's production migration script and supporting schema files, particularly:

```text
scripts/migrate_sqlite_to_postgres.py
database/complete_schema.sql
database/support_tickets_schema.sql
database/user_types_schema.sql
database_indexes.sql
services/face_embeddings.py
repositories/recognition_repo.py
repositories/attendance_repo.py
```

The production PostgreSQL schema is created by the `SCHEMA_SQL` definition in `scripts/migrate_sqlite_to_postgres.py`. It uses PostgreSQL identity columns for primary keys and defines relationships between student records, class schedules, enrollments, attendance logs, authentication records, administrative roles, support tickets, system settings, and face embeddings.

The schema supports the following major functional areas:

- academic structure management;
- user and role management;
- class scheduling and enrollment;
- attendance monitoring and report generation;
- facial recognition and embedding storage;
- support ticket management;
- administrative settings and audit records.

### C.5.5 Attendance Data Flow

The attendance workflow follows these database relationships:

```text
students
   |
   | student_id
   v
enrollments ---- class_id ----> classes
                                |
                                | course_id, room_id, instructor_id, term_id
                                v
                         courses / rooms / instructors / school_terms

students ---- student_id ----> attendance_logs <---- class_id ---- classes
                                      |
                                      | status_id
                                      v
                         attendance_status_types
```

When a student is recognized, the backend:

1. Receives a `class_id` and face image from the recognition API.
2. Loads students enrolled in that class from `enrollments`.
3. Compares the uploaded image against stored embeddings and/or face image paths.
4. Validates the class day and time using `classes`.
5. Determines the attendance status using system thresholds.
6. Inserts a record into `attendance_logs` using `student_id`, `class_id`, `timestamp`, and `status_id`.

## C.6 Face Embedding Storage

The table `student_face_embeddings` stores database-based face vectors while the original face images remain on disk or in the mounted dataset path referenced by `students.face_data_path`.

| Column | Type | Key/constraint | Description |
|---|---|---|---|
| `embedding_id` | Integer identity | Primary key | Embedding record identifier. |
| `student_id` | Integer | Foreign key with cascade delete | Student associated with the embedding. |
| `model_name` | Text | Unique with `student_id` | Face recognition model used to generate the embedding. |
| `embedding_json` | Text | Not null | Serialized JSON list of floating-point embedding values. |
| `source_image_path` | Text |  | Path of the image used to generate the embedding. |
| `created_at` | Timestamp | Default current timestamp | Embedding creation timestamp. |
| `updated_at` | Timestamp | Default current timestamp | Last update timestamp. |

The table enforces:

```text
UNIQUE(student_id, model_name)
```

This means each student has at most one stored embedding for each recognition model. If the student's face is re-registered or refreshed for the same model, the previous record is replaced.

Embedding workflow:

1. During registration, uploaded face images are saved under the configured dataset path.
2. The backend extracts a face embedding from the first saved image using DeepFace.
3. The vector is converted to JSON and stored in `student_face_embeddings.embedding_json`.
4. During recognition, the backend extracts an embedding from the submitted image.
5. It loads stored embeddings for students enrolled in the selected class.
6. It computes cosine similarity between the submitted embedding and stored embeddings.
7. If the best similarity satisfies the configured threshold, the matched student is passed to attendance logging.
8. If embedding matching fails, the system may fall back to image-to-image verification using the stored dataset image path.

This design reduces repeated file-based comparison work while preserving the original face images for fallback verification and future re-embedding.

## C.7 Authentication and Authorization Relationships

The authentication subsystem is centered on `users`.

```text
users
   |
   | role + reference_id
   v
instructors / it_admins / super_admins

users ---- updated_by ----> system_settings
users ---- user_id -------> support_tickets
users ---- assigned_to ---> support_tickets
users ---- user_id -------> ticket_replies
users ---- user_id -------> audit_logs

permissions <---- role_permissions ---- user_type
```

Important implementation note: `users.reference_id` does not declare a direct database foreign key because it can point to different profile tables depending on the value of `users.role`. The application layer resolves the reference as follows:

| `users.role` | Referenced profile table |
|---|---|
| `instructor` | `instructors(instructor_id)` |
| `it_admin` | `it_admins(it_admin_id)` |
| `super_admin` | `super_admins(super_admin_id)` |

## C.8 Support Ticket Relationships

The support ticket subsystem connects users, tickets, assignments, and replies.

```text
users ---- user_id ----> support_tickets
users ---- assigned_to -> support_tickets
support_tickets ---- ticket_id ----> ticket_replies
users ---- user_id ----> ticket_replies
```

`ticket_replies.ticket_id` uses cascade delete. If a support ticket is removed, its replies are also removed by the database.

## C.11 PostgreSQL Notes

The production migration uses PostgreSQL identity columns:

```sql
INTEGER GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY
```

This is the PostgreSQL equivalent used in the production migration for auto-generated primary keys. The migration script also resets identity sequences after importing data from SQLite so that future inserted records continue from the correct identifier values.

The production database is connected through the backend environment variable:

```text
DATABASE_URL=postgresql://<user>:<password>@db:5432/<database>
```

The Docker Compose production environment runs PostgreSQL using the `postgres:16-alpine` image and persists database files in the `postgres_data` Docker volume.

## C.12 Not Applicable or Limited Items

The following items were not documented as active schema features because they were not present in the inspected PostgreSQL schema:

| Item | Finding |
|---|---|
| Native PostgreSQL vector column | The schema stores embeddings as JSON text in `embedding_json`; no `vector` or `pgvector` column is defined. |
| Dedicated failed-recognition table | No table was found for storing failed recognition attempts. Failed recognition is returned through the API response but is not persisted in a separate table. |
| Dedicated recognition-confidence column | `attendance_logs` stores attendance status and notes but does not store confidence, distance, or similarity values. |
| Database-level polymorphic foreign key for `users.reference_id` | `reference_id` is resolved by application logic depending on `users.role`; PostgreSQL does not enforce this as a direct foreign key. |
| Dedicated class-session table | Attendance records reference `classes` and timestamps directly; there is no separate per-meeting class-session table. |

## C.13 Academic Summary

The FRAS PostgreSQL schema is organized around academic scheduling, enrollment, attendance logging, user management, and face-recognition support. The `classes` and `enrollments` tables define which students belong to a scheduled class, while `attendance_logs` records attendance outcomes using normalized values from `attendance_status_types`. The `student_face_embeddings` table stores serialized facial embeddings per student and recognition model, enabling faster recognition while preserving original face images through the student's `face_data_path`. Administrative tables such as `users`, `permissions`, `role_permissions`, `system_settings`, and support ticket tables provide operational control and maintenance functions. Overall, the schema supports the system's core workflow: register students, enroll them in classes, recognize faces during scheduled class periods, and store attendance records for monitoring and reporting.
