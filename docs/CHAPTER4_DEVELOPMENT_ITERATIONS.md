# Chapter 4 Development Iterations And Refinements

This section summarizes the major development iterations performed during the implementation of the Facial Recognition Attendance System (FRAS). The iterations are based on the repository branches, deployment files, commit history, documentation updates, and implementation fixes. They are written as development refinements rather than system failures, because each change represents a normal software engineering improvement made during construction, testing, deployment preparation, and panel-feedback alignment.

## Development Iteration Summary

Related architecture, deployment, and recognition workflow diagrams are available in `docs/CHAPTER4_SYSTEM_DEPLOYMENT_DIAGRAMS.md`.

| Iteration | Development Area | Issue Encountered | Correction Or Refinement Applied | Result |
|---|---|---|---|---|
| 1st Iteration | Initial authentication and registration | Early login and registration logic still depended on hardcoded data and incomplete backend integration. | JWT authentication, user lookup, password validation, route guards, and backend-connected login workflows were added. | Login became database-driven and role-aware, allowing users to access modules according to their permissions. |
| 2nd Iteration | Attendance database and status logic | Attendance records needed standardized status handling instead of inconsistent text-based values. | A standardized attendance status type table was added, and attendance logs were updated to reference status identifiers. | Attendance records became easier to query, display, filter, and export consistently. |
| 3rd Iteration | Student enrollment from registration | Registered student schedule entries were not always reflected in the enrollment table. | The registration workflow was corrected so submitted course-section entries populate enrollment records. | Registered students became properly linked to classes, allowing recognition to check only students enrolled in the selected class. |
| 4th Iteration | Schedule validation and attendance timing | Attendance could be attempted outside the proper class period or without reliable schedule validation. | Schedule checks were added using class day, start time, and end time, and automatic absent marking was introduced. | Attendance recording became tied to valid class schedules, improving the integrity of attendance records. |
| 5th Iteration | Role-based navigation and access control | Navigation and administrative pages needed to reflect the permissions of different user roles. | Auth guards, admin guards, super admin checks, permission-aware navigation, and backend permission dependencies were implemented. | Users only saw and accessed modules appropriate to their role, strengthening RBAC enforcement. |
| 6th Iteration | Admin tools and support workflow | Administrative workflows needed user management, password reset, and support handling. | User Management, password reset, IT admin interface, super admin functions, and support ticket management were added. | Administrative operations became centralized and easier to manage through protected interfaces. |
| 7th Iteration | System settings save workflow | System settings required a clearer update flow and confirmation behavior. | A save modal and staged settings workflow were added for super administrator configuration changes. | Configuration updates became more deliberate and easier to review before saving. |
| 8th Iteration | Attendance duplicate prevention | Repeated face recognition attempts could create duplicate attendance records for the same student and class. | Duplicate attendance checks and a configurable attendance buffer were implemented. | Repeated recognition attempts were controlled, preventing unnecessary duplicate attendance entries. |
| 9th Iteration | Face registration path correction | Existing student face images were present in dataset folders, but some database records did not contain the correct `face_data_path`. | Database backfill scripts and registration repository updates were added to populate and verify face data paths. | The recognition pipeline could reliably locate stored student images for comparison. |
| 10th Iteration | Recognition dataset and embedding improvement | Recognition needed better performance and more reliable lookup than repeated image-to-image comparison alone. | Face embedding generation, embedding storage, embedding backfill scripts, and embedding-first recognition were added. | Recognition became more efficient by comparing the captured image against stored student embeddings before using legacy image verification fallback. |
| 11th Iteration | AWS deployment exploration | An AWS-based deployment branch introduced cloud deployment configuration, task definitions, S3-related handling, and deployment complexity. | AWS deployment work was isolated in an `awsdeploy` branch and later deployment direction shifted toward a simpler VPS/Docker approach. | The project retained deployment learnings while moving toward a more manageable deployment strategy for capstone demonstration. |
| 12th Iteration | S3 optionality and local dataset fallback | The recognition pipeline needed to work whether face images were available locally or through S3-style cloud storage. | The system was adjusted so local dataset folders are used first, while S3 download behavior is only used when explicitly enabled through `USE_S3`. | The system became more flexible and could run in local, VPS, or optional cloud-storage environments. |
| 13th Iteration | Docker and deployment configuration | Deployment required a stable backend/frontend container setup and correct API routing. | Docker production configuration, Nginx proxy rules, `.env.example`, deployment checking scripts, and secret generation utilities were added. | Deployment became more repeatable and safer because configuration was separated from source code. |
| 14th Iteration | GoDaddy VPS deployment revision | The project needed a more cost-efficient and manageable hosting path than the earlier AWS deployment direction. | A GoDaddy VPS deployment guide was created using Docker Compose, FastAPI, Angular through Nginx, and PostgreSQL migration support. | Deployment became easier to explain, reproduce, and maintain for thesis demonstration and production-style hosting. |
| 15th Iteration | PostgreSQL migration preparation | Production deployment required a database option beyond the local SQLite demo database. | SQLite-to-PostgreSQL migration scripts, PostgreSQL Docker service configuration, and backup utilities were added. | The system gained a clearer path from local demo storage to production database deployment. |
| 16th Iteration | Linux path and dataset mounting | Dataset paths created on Windows needed to work correctly in Linux containers and VPS deployment. | Backslash normalization, `DATASET_PATH`, writable dataset mounts, and host dataset bind mounts were added. | Face image storage became more portable across Windows development and Linux deployment environments. |
| 17th Iteration | UI consistency and panel feedback | Some administrative screens, support forms, reports, and labels required clearer and more consistent presentation. | Panel feedback updates revised user management wording, support placeholders, collapsible filters, reports display, and visual terminology. | The interface became more polished, consistent, and presentation-ready. |
| 18th Iteration | Room schedule data quality | Different room input formats could create duplicate room records and affect schedule lookup. | Room normalization, duplicate-room cleanup scripts, and database-level duplicate protection were added. | Room schedule management became more reliable and avoided conflicting room entries. |
| 19th Iteration | Attendance reports refinement | Report generation needed clearer validation, empty states, filters, and export behavior. | Attendance Reports UI was polished with required class/professor checks, date validation, status filters, grouped records, and clearer export actions. | Reports became easier to use for formal attendance review and thesis demonstration. |
| 20th Iteration | Analytics and face registration readiness | The dashboard needed stronger visual indicators and clearer wording for face registration coverage. | Analytics charts, face registration readiness visuals, and presentation-friendly labels were added. | Administrators gained clearer insight into student registration, attendance activity, and recognition readiness. |
| 21st Iteration | Demo data reliability | Demonstration data could become inconsistent after repeated testing. | A repeatable demo data reset workflow was added to rebuild users, students, instructors, rooms, classes, logs, tickets, and face-registration coverage. | The project became easier to prepare for defense, testing, and demonstration. |
| 22nd Iteration | Attendance timestamp accuracy | Attendance log dates and times required correction because UTC conversion could shift displayed records. | Backend timestamp handling was refined so attendance logs store and display Manila wall time consistently. | Attendance logs and date filters became more accurate for the target deployment timezone. |
| 23rd Iteration | Recognition result refresh behavior | Attendance recognition results needed to refresh the UI after a successful recognition attempt. | The recognition workflow was updated so the frontend refreshes the attendance data after recognition. | Users could immediately see updated attendance records after a recognition event. |

## Specific Development Problems And Later Corrections

| Development Problem Encountered | Correction Or Improvement Made In Later Iterations | Academic Interpretation |
|---|---|---|
| AWS deployment increased infrastructure complexity and introduced several cloud-specific configuration files. | Deployment direction was revised toward Docker/Nginx VPS deployment with GoDaddy documentation and environment-based configuration. | This was an infrastructure revision that improved cost control, maintainability, and deployment reproducibility. |
| Recognition initially depended heavily on local image paths and could be affected when dataset paths were missing or platform-specific. | Face data paths were backfilled, Windows path separators were normalized for Linux, and `DATASET_PATH` was introduced. | This was an operational portability improvement for moving the system from development to deployment. |
| Cloud storage support needed to coexist with local dataset use. | S3 download behavior was made optional through `USE_S3`, while local dataset folders remained the default recognition source. | This improved deployment flexibility without making cloud storage mandatory. |
| Student face images existed but recognition could not always locate them because `face_data_path` records were missing. | Registration logic was updated to save and verify `face_data_path`, and helper scripts were created to fix existing records. | This strengthened the link between student registration and recognition processing. |
| Repeated recognition attempts could produce duplicate attendance records. | Duplicate attendance lookup and configurable buffer validation were added before inserting attendance logs. | This improved data integrity during automatic or repeated recognition attempts. |
| Attendance could be attempted outside the correct schedule context. | Schedule day and time validation were added before recording attendance. | This aligned the recognition workflow with academic attendance rules. |
| Attendance log timestamps could be shifted by UTC handling. | Timestamp parsing and storage were revised to use Manila wall time consistently. | This improved accuracy for date-based attendance review in the local context. |
| Room schedule entries could create duplicate room records when users typed room labels in different formats. | Room numbers were normalized and duplicate-room cleanup and unique-index protection were added. | This improved schedule data quality and prevented conflicting room records. |
| Some role and permission behaviors required better consistency between frontend navigation and backend protection. | Permission normalization, route guards, permission-aware navigation, and backend permission dependencies were strengthened. | This improved RBAC consistency and reduced unauthorized navigation paths. |
| Support ticket and user management pages required clearer feedback and panel-ready presentation. | Support placeholders, management panels, filter behavior, and user-facing labels were revised through panel feedback updates. | This was an interface consistency improvement that enhanced usability. |
| Attendance reports needed clearer filters and validation for class and professor report modes. | Report form validation, grouped results, collapsible advanced filters, and clearer export buttons were added. | This improved report usability and made generated outputs more suitable for formal review. |
| Analytics terminology such as embedding coverage was too technical for presentation. | The dashboard wording was revised to face registration readiness and paired with visual analytics. | This improved communication for non-technical evaluators while preserving the technical function. |
| Deployment configuration contained environment-sensitive values and needed safer setup guidance. | `.env.example`, secret generation, deployment check scripts, Docker cleanup, and Nginx proxy configuration were added. | This improved deployment hygiene and reduced configuration errors. |
| Demo data could become unstable after repeated tests. | A reset workflow was added to rebuild a consistent demo database. | This improved repeatability for testing, presentation, and thesis validation. |

## Thesis-Ready Paragraph

The development of FRAS followed an iterative refinement process. Early iterations focused on implementing the core attendance workflow, including login, registration, facial recognition, attendance logging, and schedule-based validation. Later iterations improved role-based access control, administrative modules, support ticket handling, system settings, and report generation. As the system moved closer to deployment, additional refinements addressed infrastructure and operational concerns, including AWS deployment exploration, migration to a more manageable Docker/Nginx VPS deployment path, optional S3 support, PostgreSQL migration preparation, dataset path portability, and environment-based configuration. Final iterations focused on interface consistency, panel-feedback corrections, analytics visualization, demo data reliability, duplicate attendance prevention, room schedule data quality, and Manila-time timestamp accuracy. These iterations show that the system was progressively improved through functional testing, deployment preparation, UI review, and operational validation.
